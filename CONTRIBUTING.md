# Development

Use Python 3.13 for runtime parity. In a virtual environment:

```sh
python -m pip install -r .github/dev/requirements-dev.txt
python -m unittest discover -s .github/tests -p 'test_*.py' -v
node --check assist_ai_router/app/static/app.js
node --test .github/tests/ui.test.cjs
cd assist_ai_router
python -m app.server --dev --data ../.local
```

Development mode binds both listeners to loopback. It uses only `.local` files and refuses unresolved secrets. Production requires Supervisor, restricts ingress to `172.30.32.2` and never trusts forwarded IP headers for access control. Never use real credentials in test fixtures.

Container validation:

```sh
docker build --platform linux/amd64 -t assist-ai-router:test assist_ai_router
docker run --rm --entrypoint /bin/bash -v "$PWD/.github/tests:/tests:ro" assist-ai-router:test /tests/runtime.sh
docker build --platform linux/arm64 -t assist-ai-router:arm64 assist_ai_router
docker run --rm --platform linux/arm64 --entrypoint python assist-ai-router:arm64 -c 'from app.router import sdk; sdk(); from app.server import Server'
```

`.github/workflows/ci.yml` remains generated by the shared hass-workflows engine. It validates, builds both declared architectures, smoke-tests and publishes according to the engine's existing default-branch rules. `.github/workflows/quality.yml` runs repository-specific tests including metadata/translations before any merge. The pinned engine revision adds calendar app versions without changing callers of other repositories.

The shared caller needs the repository secret `ORCHESTRATION_PAT` with Contents: Read access to the private `seb5594/hass-workflows` repository. Catalog notification additionally needs the engine's existing catalog permissions; it is optional for local builds. GitHub Actions billing/spending restrictions must be resolved in the account before hosted jobs can start.

Starting with v1.0.0, release versions use semantic versioning (`MAJOR.MINOR.PATCH`); Git tags use the `v1.0.0` form. The app remains experimental. Earlier releases used calendar versions. The shared engine supports both formats; no caller changes are required. Bump app/catalog.py VERSION, config.yaml, Dockerfile BUILD_VERSION and CHANGELOG.md together. The runtime metadata generator is `.github/dev/generate_metadata.py`; UI translations live in app/static/i18n.json. Run the generator after settings/schema or translation changes. Never change a published image under the same app version.

Upstream upgrades must update the Dockerfile tag **and multiarch digest**, app/catalog.py LITELLM_VERSION and dev requirement pin together. Startup enforces the reviewed SDK version. Run the actual SDK tool-call test against its local upstream stub, both image builds and acceptance checks before release. The web UI version check only reports stable upstream releases; it does not update packages.

Before declaring stable, verify on real Home Assistant OS: ingress/protection mode, Supervisor option saves and raw secret references after restart, native LiteLLM setup/model discovery, Assist device tools, MCP links and permission choices, provider 429/Retry-After behavior, backup restore and responsive browser rendering. Backend tests cannot prove these hardware/provider/UI outcomes.

No automatic test uses external AI credentials or controls actual devices. No prompts/completions are stored. The database holds request metadata and conservative quota reservations, including interrupted calls.
